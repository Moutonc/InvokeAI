KEY FINDINGS

1. CONFIG STRUCTURE (configs/lora.py)
   ├─ LoRA_Config_Base: Base class with common fields
   ├─ Format-specific classes: OMI, LyCORIS, Diffusers formats
   ├─ Each validates at construction time
   ├─ Uses state dict heuristics to identify model type
   └─ Models default settings: weight (-1 to 2)

2. LOADER IMPLEMENTATION (load/model_loaders/lora.py)
   ├─ @ModelLoaderRegistry.register() decorators for discovery
   ├─ Supports multiple base models: Flux, SDXL, SD1, SD2
   ├─ Supports multiple formats: OMI, LyCORIS, Diffusers
   ├─ _get_model_path(): Resolves file paths
   ├─ _load_model(): Core loading pipeline
   │  ├─ Load state dict from disk
   │  ├─ Apply format conversions
   │  ├─ Convert to internal model representation
   │  └─ Convert to target dtype
   └─ Detailed format detection for Flux models

3. REGISTRATION SYSTEM
   ├─ Model Installation API: POST /v2/models/install
   ├─ Flow: File → _probe() → Factory → Config → Database
   ├─ ModelConfigFactory pattern:
   │  ├─ Uses Pydantic discriminated unions
   │  ├─ Tries all config classes in order
   │  ├─ Returns first matching config
   │  └─ Falls back to Unknown_Config
   ├─ ModelRecordService: Database storage
   └─ Cloud models already supported (CloudModelConfig)

4. INVOCATION PATTERNS (flux_lora_loader.py, etc.)
   ├─ Single LoRA: FluxLoRALoaderInvocation
   ├─ Collection: FLUXLoRACollectionLoader
   ├─ Model Fields:
   │  ├─ ModelIdentifierField: key, hash, name, base, type
   │  └─ LoRAField: (lora=ModelIdentifierField, weight)
   ├─ Key Patterns:
   │  ├─ Lazy loading: Just append LoRAField, don't load
   │  ├─ Accumulation: Multiple LoRAs can be chained
   │  ├─ Duplicate prevention: Check before adding
   │  └─ Weight control: Each LoRA has own weight

5. COMPLETE LIFECYCLE
   ├─ Phase 1 - Preparation (Registration)
   │  └─ File → detect → validate → store in database
   ├─ Phase 2 - Composition (Building Workflow)
   │  └─ Select model → create LoRAField → append to model list
   ├─ Phase 3 - Execution (Running Workflow)
   │  └─ Load on demand → patch layers → generate → release
   └─ Model Caching: Efficient reuse across runs

6. CLOUD MODEL PATTERN
   ├─ Config: CloudModelConfig class structure
   ├─ Loader: Create API client instead of loading file
   ├─ Registration: Manual API endpoint (no disk probing)
   ├─ Path Resolution: Return dummy path for cloud models
   └─ Invocation: Same pattern as LoRA (lazy loading)

KEY ARCHITECTURE PATTERNS

1. Discriminated Union Pattern
   └─ Type-safe polymorphism with Pydantic validation
   └─ All model types in single union with discriminator

2. Registry Pattern for Loaders
   └─ @ModelLoaderRegistry.register() decorator
   └─ Automatic discovery by (base, type, format) tuple

3. Config Factory Pattern
   └─ ModelConfigFactory.from_model_on_disk()
   └─ Tries all config classes until one succeeds

4. Lazy Model Loading
   └─ Models NOT loaded in invocations
   └─ Loaded only when needed for inference

5. Separation of Concerns
   └─ Config: What the model is
   └─ Loader: How to load it
   └─ Invocation: How to use it
   └─ Infrastructure: Caching and model management

KEY INSIGHT: The Pattern You Should Follow

LoRA Models:
  File → Config → Loader → Field → Invocation → Layer Patching

Cloud Models (Same Pattern):
  API → Config → Loader → Field → Invocation → API Call

The architecture is IDENTICAL. Only the implementation details change:
  - Config detects from files vs. manual registration
  - Loader loads state dict vs. creates API client
  - Application patches layers vs. makes HTTP calls
